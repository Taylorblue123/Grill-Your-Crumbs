# 产品唯一红线：真缺口永不编造

产品身份红线清单收窄为**一条**：针对目标要求「问过了也确实没有」的真缺口（gap），永不被写进任何产出物假装用户有——缺口诚实展示给用户，而不是被文案糊上。参考文档中的其余三条候选（逐片段可回溯出处、不出百分比/匹配分、撤回向下游联动）**不是**独立红线：可回溯出处降为本红线的支撑不变量，后两条降为普通设计机制（V1 维持现有设计，但可随时重议，phase 2 匹配形态不受约束）。

裁决于 2026-08-24，经创始人拷问会话确认（[Ticket #11](https://github.com/Taylorblue123/Grill-Your-Crumbs/issues/11)）。

判断标准：「如果违背了它，这个产品还是不是它自己？」只有「不编造」过测试——违背它，产品就变成自己定义里要反对的那类竞品（为匹配 JD 而润色、夸大、硬凑经历的工具），第一购买理由「发现真实经历」直接坍塌。红线越少越有力：一条真红线胜过四条口号。

## Considered Options

- **四条全部钉死为红线**（原型与 schema 草案的隐含立场，`prototype/README.md`「一条红线」、`docs/backend-schema.md`「fillable=false 是一条产品红线」等）——被否：按身份测试只有「不编造」不可谈判，其余是可被更好设计取代的选择；过度钉死会用未经用户验证的审美锁死 phase 2（尤其匹配分）并抬高 V1 工程量。
- **「不出百分比/匹配分」钉死为红线**——被否，降为普通机制：V1 维持「可数条目、不出分」的现有设计（账本、六格矩阵、「对上 12 · 确实没有 2」），但无真实用户证据支撑其为身份；phase 2 匹配引擎形态自由重议。
- **「撤回向下游联动」钉死为红线**——被否，降为普通机制：违背它产品变差，但不至于不是它自己；某种「可撤回」本身是 PIPL 法定要求，法务层由隐私与合规票（#20）处理。
- **四条全降为机制、不设红线**——被否：「不帮用户编造」正是与竞品的分界线，需要一条替未来的自己说「不」的身份约束（增长压力下「稍微润色一点转化率能涨」的那一刻）。
- **红线仅靠提示词措辞强制**——被否：把红线兑现押在 LLM 不幻觉上，破的地方恰好是第一购买理由。

## Consequences（架构性不变量）

1. **缺口不进生成上下文**（服务端强制，本红线的主强制点）：组装产出物生成 prompt 时，只放入已确认的事实；判定为真缺口的目标要求不进入生成器输入——生成器没见过的东西谈不上围绕它编造。这是服务端 prompt 组装逻辑，不要求数据库层约束。
2. **真缺口是推导出来的，不是 LLM 断言的**：「真缺口」的操作性定义＝问过了、答了、但没有任何一条未撤回的事实匹配上它——由数据推导（查询结果），不由生成模型自行标注。
3. **事实写入时必须记录来源**（支撑不变量）：每条事实在抽取落库那一刻记录其出处（来自哪轮对话/哪份材料），来源字段不可为空——出处只能在写入时记录，事后无法补。三色出处 UI 读取此字段；无法绑定事实的成稿句子标红等用户确认（语义残余风险的兜底）。
4. **明确不作为不变量**（给后续架构图松绑）：原型 schema 草案中的出稿事务校验（「gap 片段查询必须返回 0 行」的 DB 约束）、撤回的实时联动降级视图、requirement_match 派生视图机制——均降为将来可选的加固手段或普通设计选择，重写后端时不强制实现。
5. **不出分仅为 V1 设计约定**：面向用户不出聚合分数（完成度百分比、匹配分）是 V1 的普通机制而非红线；phase 2 匹配引擎的呈现形态（含是否出分）自由决定。若做用户验证实验，「分数 vs 可数条目」偏好是候选实验项。
